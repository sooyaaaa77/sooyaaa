# 05 · Git 版本管理记录

> 项目：个人介绍网站｜目的：记录本项目的版本管理约定与关键提交过程，作为课程过程材料的一部分。
> 相关文档：[实施计划](03-plan.md)｜[部署手册](04-deployment.md)｜[项目总结](08-summary.md)

## 1. 为什么用 Git

课程要求「使用 Git 工具进行版本管理，记录关键提交信息和过程」。除了满足要求，Git 在本项目里实际解决了三件事：

1. **可回滚**：页面、样式、文档改动频繁，改坏了能回到上一个可用版本，不用手动复制「final-2-真的最终版」。
2. **过程可见**：`git log` 本身就是一份按时间排列的开发记录，答辩和面试时可以直接展示「先做什么、后做什么、为什么」。
3. **部署可追溯**：每次上线对应一个提交，线上出问题能定位到「上的是哪一版」，也能用 `git checkout <hash>` 取回旧版本重新部署。

## 2. 版本管理约定

### 2.1 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 唯一长期分支，始终可部署 | 本地开发直接提交到 `main`；单人项目不引入 `dev`，避免合并开销 |
| 临时分支（可选） | 试验性改动（如大改版式） | 从 `main` 切出，验证通过后合并回 `main`，失败直接删除 |

个人项目 + 两周周期，采用「`main` 单分支 + 小步提交」比 Git Flow 更合适：分支模型越复杂，合并冲突和收尾成本越高。

### 2.2 提交信息规范

采用 Conventional Commits 的简化版：

```
<type>: <简短说明>
```

| type | 含义 | 本项目示例 |
|---|---|---|
| `chore` | 仓库初始化、配置、构建/部署辅助文件 | 初始化仓库、新增 Nginx 配置 |
| `docs` | 只改文档 | 需求分析、部署手册、README |
| `feat` | 新增页面、区块或交互功能 | 页面骨架、项目经历区块 |
| `style` | 只改样式、布局、响应式，不改功能 | 响应式适配、白底改版 |

约定细节：

- 标题用中文写「做了什么」，控制在 50 字以内，句末不加句号。
- 一次提交只做一件事：内容和样式分开、代码和文档分开，便于单独回滚。
- 需要解释「为什么」时，在提交正文里写，不要只改标题。
- 不使用 `update`、`fix bug`、`修改一下` 这类无法检索的信息。

### 2.3 提交前检查

```bash
git status                     # 确认没有误改、没有把 local.conf / *.pem 加进来
node --check main.js           # JS 语法
bash -n scripts/deploy.sh      # Shell 语法
python -m http.server 8080     # 浏览器里再看一眼
git diff --cached              # 提交前过一遍暂存区内容
```

## 6. 常用命令与排错

```bash
# 看历史（推荐带图，能看出分支与提交顺序）
git log --oneline --graph --decorate

# 看某次提交改了什么
git show 9e9f658 --stat
git show 9e9f658 -- index.html

# 撤销未提交的修改（危险：会丢改动，先确认）
git restore index.html

# 回到某个历史版本查看（不丢当前分支）
git checkout 1ff9848 -- index.html

# 提交信息写错了（还没 push）
git commit --amend -m "feat: 修正后的说明"

# 误把文件加进暂存区
git restore --staged deploy/local.conf

# 查看某一行是谁在哪个提交里改的
git log -L 1,20:index.html
```

常见问题：

| 情况 | 处理 |
|---|---|
| 提交里混进了 `local.conf`、`*.pem`、日志 | `.gitignore` 已覆盖；若已提交，`git rm --cached <文件>` 后再提交 |
| Windows 换行导致整文件 diff | 仓库已设 `core.autocrlf false`，避免 CRLF/LF 混用造成的假改动 |
| 提交后发现漏了文件 | 未 push 时 `git add <文件> && git commit --amend --no-edit`；已 push 则补一个新提交 |
| 想撤销最近一次提交但保留改动 | `git reset --soft HEAD~1` |

## 7. 与部署的衔接

- 每次上线前先 `git status` 确认工作区干净，保证「线上版本 = 某个提交」。
- `scripts/deploy.sh` 只上传 6 个站点文件，不打包整个仓库，避免把 `docs/`、`.git/`、截图产物传到服务器。
- 线上出问题：`git log` 找到上一个可用提交 → `git checkout <hash> -- <文件>` 取回 → 重新执行部署脚本。
- 服务器上的 `/var/www/mysite` 不参与版本管理，仓库是唯一事实来源；服务器只存放构建产物（本项目的产物就是源文件本身）。

## 8. 复盘

做得好的：

1. **文档先行**让后续每次提交都有明确目标，没有出现「不知道下一步做什么」的空转。
2. **提交粒度小**，出问题能精确回退；代码、文档、部署物料分开提交，改版的回滚与文档修订互不牵连。
3. **部署物料进仓库**，上线流程可复现，换一台服务器也能照文档走一遍。
4. **改版也走完整流程**：先改代码，再同步文档与测试，最后补提交记录和标签，而不是「改完就算」。

可以改进的：

1. 提交时间集中在同一天，因为页面是一次性生成的；真实开发中应更均匀地分布，便于观察节奏。
2. 没有使用 PR/Issue 流程；单人项目可以接受，但团队协作时应补上分支保护与代码评审。
3. 尚未配置 CI（如 GitHub Actions 做 HTML/链接检查），后续可以把第 2.3 节的检查脚本化。
