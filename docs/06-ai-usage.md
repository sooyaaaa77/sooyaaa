# AI 使用说明与协作记录

> 课程允许使用 AI 辅助完成本项目。这份文档说明：**哪些环节用了 AI、怎么用、人工做了什么把关**，
> 以及遇到问题时如何判断与修正。目的不是"证明没用 AI"，而是能对每一行代码和每一步操作讲清楚来龙去脉。

---

## 一、基本立场

1. 本项目重点是**流程规范**（Markdown 文档、Git 版本管理、服务器部署），不是考察手写代码能力，老师明确允许 AI 辅助。
2. 使用 AI 的底线：**不提交自己讲不清楚的代码**。凡是写进仓库的内容，都经过本地运行或静态检查，并能说明"它解决什么问题、为什么这么写"。
3. AI 生成的内容一律视为**初稿**：需要人工核对事实（学校、项目、成绩等绝不虚构）、核对链接、核对命令，再决定是否采纳。
4. 所有 AI 参与的产出都通过 Git 提交留痕，提交信息说明改动范围，便于老师和我自己回溯。

---

## 二、AI 参与范围一览

| 环节 | AI 参与度 | 人工负责 |
| --- | --- | --- |
| 需求梳理、文档结构（docs/01–03） | 高：给出提纲与初稿 | 确认真实需求、删掉不适用内容、决定取舍 |
| 视觉方案（参考 pudding.cool 的排版与动效） | 中：给出版式/动效参数与 CSS 初稿 | 确定风格方向、判断哪些效果值得做 |
| HTML 结构 / CSS 样式 / 原生 JS 交互 | 高：生成代码 | 逐段阅读、本地预览、决定删减，确保能解释 |
| 响应式与可访问性 | 中：提供断点与 aria 写法 | 实际缩放窗口验证、键盘测试 |
| Nginx 配置与部署脚本 | 高：给出配置模板与脚本 | 在服务器上真实执行、按报错修正 |
| 文档撰写（部署手册、测试、总结） | 高：生成初稿 | 对照真实操作过程校正，补充实际遇到的问题 |
| Git 提交信息 | 低：只做格式建议 | 每次提交前自己确认改了哪些文件 |

**没有使用 AI 的部分**：真实个人信息、项目经历、成绩、照片、简历内容——这些必须本人提供，AI 不得编造。

## 三、实际协作流程

```text
① 我把需求/约束说清楚（含禁止项）
        ↓
② AI 给出方案与初稿（文档或代码）
        ↓
③ 我判断：是否符合课程要求？是否讲得清楚？是否引入额外依赖？
        ↓  否 → 要求重写/简化
        ↓ 是
④ 落地到仓库，本地运行/静态检查
        ↓
⑤ 有问题 → 把报错/现象贴回去 → AI 修正 → 再验证
        ↓
⑥ git commit（说明这次改了什么、为什么）
```

### 提示词示例 1：约束先行

> "纯静态 HTML/CSS/JS，不引入任何第三方库和外链字体。参考 pudding.cool 的编辑排版风格，
> 做一个单页个人作品集，要求：深色/浅色主题切换、移动端可用、尊重 prefers-reduced-motion。
> 先给信息架构和设计取舍，不要直接写代码。"

先要方案、再要代码，能避免 AI 一上来就堆砌框架和不必要的复杂度。

### 提示词示例 2：带验收条件

> "给 hero 区块加一个滚动提示和 'OPEN TO WORK' 贴纸。要求：不给按钮加 JS 依赖；
> 移动端 620px 以下隐藏贴纸；所有装饰元素 aria-hidden='true'。"

把"验收条件"写进提示词，生成的代码更容易一次通过，也方便事后检查。

### 提示词示例 3：要求解释而非只给结果

> "解释这段 IntersectionObserver 代码每一行在做什么，以及为什么 threshold 用 0.12、
> rootMargin 用 -8%。如果我想让元素只出现一次动画，应该在哪里 unobserve？"

用于确认自己真的理解，而不是复制。

## 四、AI 出错与人工纠错记录（真实案例）

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | 首版样式没有媒体查询，手机上一屏挤成一列文字 | AI 默认按桌面宽度写，未主动考虑响应式 | 要求补充 1080/920/620 三档断点，并手动拖窗口验证 |
| 2 | 想把参考站点的视差/光标效果全部照搬 | 参考站的效果依赖较多 JS 与实时跟随，性能和可访问性收益不成正比 | v0.1 只保留进场、数字滚动和一个简单光标；v0.2 按用户反馈把光标与视差全部删除，恢复系统默认鼠标 |
| 3 | 生成的占位简历 PDF 是 ASCII 文本 | 直接拼 PDF 结构是可行但脆弱的做法 | 保留为占位并在清单中标注"发布前必须替换" |
| 4 | Git 在 Windows 下可能出现换行符差异 | 不同系统 CRLF/LF 不一致 | 仓库设置 `core.autocrlf false`，文件统一保存 |
| 5 | HTML 静态检查脚本把 `<meta />` 误报为未闭合 | 检查脚本未处理自闭合标签 | 修正检查逻辑后复检，确认是误报而非页面问题 |
| 6 | 部署脚本在远程 `sudo` 处卡住 | 非交互 SSH 下 sudo 等待密码 | 文档写明需配置 NOPASSWD sudoers，并给出命令 |

> 这些错误都记录在案，说明 AI 产出**必须验证**；验证手段见 `docs/07-testing.md`。

## 五、人工把关清单（每次采纳 AI 产出前）

- [ ] 代码能在本地打开/运行，控制台无报错
- [ ] 没有引入课程禁止的工具（面板、一键包、托管平台）
- [ ] 没有外链字体、外链 JS/CSS（离线也能正常显示）
- [ ] 没有把示例信息当成真实信息提交（姓名/学校/项目待本人替换）
- [ ] 交互可键盘操作，装饰元素有 `aria-hidden`
- [ ] 我能用自己的话解释这段代码的作用
- [ ] 提交信息说明了改了什么、为什么改

## 六、如何向老师/面试官说明

三句话版本：

1. "网站用纯静态 HTML/CSS/JS 实现，视觉与动效参考了 pudding.cool 的编辑排版风格。"
2. "代码和文档在 AI 辅助下完成，我负责需求、取舍、验证和部署；每一步都有 Git 提交记录。"
3. "部署走的是最原始的方式：Ubuntu 上 apt 装 Nginx，手动上传静态文件，用公网 IP 访问——没有用任何面板或一键包。"

面试官更关心"你能不能讲清楚为什么这样做"，而不是"是不是你手打的"。
因此准备 2–3 个能深入讲的技术点，例如：

- 为什么纯静态方案对这个需求足够，什么情况下才需要后端；
- IntersectionObserver 做进场动画与数字计数的原理、`unobserve` 的作用；
- Nginx 的 `try_files`、`gzip`、缓存头分别在解决什么问题。

## 七、AI 使用红线

1. **不虚构经历**：项目、实习、奖项、数据统计必须真实，宁可少写。
2. **不上传隐私**：不把身份证、家庭住址、手机号、服务器密码、私钥发给 AI 或提交到 Git。
3. **不提交不理解的代码**：讲不清作用的代码一律删掉或重写。
4. **不盲信 AI 的命令**：涉及 `rm -rf`、`chmod 777`、开放全部端口等操作，先理解再执行。
5. **不把 AI 生成的"事实"当事实**：命令参数、云厂商路径、法规（如备案）都可能过时，以官方文档为准。
